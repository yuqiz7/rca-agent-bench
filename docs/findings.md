## 1. Agent 侧失败模式归类

开发集 19 张、v1 prompt 的九张错卡里 **6 张是「服务对、类别错」**，
定位不是短板，机制判断才是（决策 024 trade-off）。前三种错法来自那一轮；
§1.4 由第二留出集补上（决策 031），§1.5 由开箱 haiku 臂补上（决策 034）。

### 1.1 crash ↔ blackhole 在 harvest 视角下被同化

**现象**：v1 在 4 张 crash 卡里错 3 张，全部答成 blackhole。

**成因**：证据包是 **harvest 视角**（决策 016）——注入撤除之后才取快照，
blackhole 期间被 TCP 重传挂住的请求在撤除瞬间**一次性回放**，把注入窗填满。
于是「crash 吵、blackhole 哑」这条决策 010 划的分界线，在 agent 看到的数据里
比在 immediate 视角下接近得多。指纹侧的实测：blackhole 的 `after` 窗日志
**151 条 vs 自身基线 61 条**（2.5 倍），crash 的 `after` 是 42 条、低于基线 73。

**v2 修法**：把判别从「最后是否静默」改成「故障**头几秒**调用方在做什么」——
连接类硬报错＋立即静默＝进程没了；被堵住数秒＝丢包。并写明报错**条数可以很少**
（调用方退避后不再产生流量），以及失败调用的耗时**低于**基线（fail-fast 比成功还快）。

**效果**：crash 类 top-1 **0/4 → 2/4**。

**F-5 的教训（同一次改动的代价）**：同一段里我把 `valkey-cart` 这种**长连接靶子**的
「超时台阶」形态写成了 blackhole 的**通例**，而 fingerprints.md 归档的通例是
「哑」——0 span、0 报错。台阶只是**有客户端超时的无 SDK 靶子**的例外。
prompt 里那句「p50 抬升到秒级、几乎无报错」与 latency 的描述几乎同形，
两张普通 SDK 靶子的 blackhole 卡因此被判成 latency，**blackhole 类 3/4 → 1/4**。

> **知识注入的收益和风险是同一个量级的。** 写对的两段各把目标类别从 0 抬到 2/4 与 1/2；
> 写错的一段把一个本来就对的类别从 3/4 打到 1/4。素材准确性不是文档卫生问题，是准确率问题。

**证据**：决策 025、F-5、`artifacts/agent_runs/devset_v2_20260828/report.md`、
`docs/fingerprints.md` 的两节 blackhole 指纹。

### 1.2 mem_leak 流程缺失

**现象**：v1 在 2 张 mem_leak 卡上全错，都答成 latency；其中一张只用了 **2 步**就交卷。

**成因**：`container_memory_mib` 一直在工具面里，但 prompt 从没把「先查内存曲线」
写成必经步骤。内存泄漏的表现就是**慢**，不查曲线就无法与 latency 分开。

**v2 修法**：慢而不报错、config diff 为空的服务**还没有**被证明是 latency；
要求先拉内存序列看是否单调抬升，看过曲线再下结论。

**效果**：mem_leak **0/2 → 1/2**；平均步数 4.42 → 5.11（多出来的步就花在这里）。

**证据**：决策 024 trade-off、决策 025、commit `81b17d0`。

### 1.3 低流量靶子的调用方顶包

**现象**：agent 把答案答成真凶的**邻居**——`blackhole-cart-01` 答 `valkey-cart`、
`misconfig-cart-75` 答 `valkey-cart`、`crash-product-catalog-01` 答 `flagd`。

**成因**：低流量靶子自身 span 稀少，调用方的 span 反而密集，
「谁的信号强就答谁」在这类卡上系统性偏向调用方或旁邻。
基线①（规则臂）在留出集上错的两张是同一种错法——
`blackhole-astronomy-db-01` 停在调用方 `product-catalog`、
`blackhole-email-01` 停在入口 `frontend-proxy`。**三臂共有的失败模式，不是某一臂的缺陷。**

**证据**：F-7、`artifacts/agent_runs/holdout5_20260828/report.md`。

**第二留出集补一例**：11 张里 agent 只错 2 张，**两张都是 `ad` 卡**
（`latency-ad-800` 答 `frontend`、`blackhole-ad-01` 答 `frontend`），
错法与本节同型 —— 答案落在真凶的**唯一调用方**身上。
但这两张的成因比「谁的信号强答谁」更具体，单列为 1.4。

### 1.4 未枚举的边被当成已排除的边（2026-09-06，第二留出集）

**现象**：`latency-ad-800` 与 `blackhole-ad-01` 两张卡，agent 都答 `frontend/latency`，
真值分别是 `ad/latency` 与 `ad/blackhole`。两次的收尾理由几乎逐字相同：

> 「额外的 ≈800 ms（另一张：15000 ms）完全落在 `frontend` 自己的 `/api/data` span 里，
> **没有对应的慢下游调用**（astronomy-db 与 product-catalog 都正常），
> 因此是注入在 `frontend` 自身的延迟。」

**成因**：两次它都在第 1 步取了 `topology`，而 `evidence/_shared/topology.json` 的
33 条边里，`frontend → ad` 是 `frontend` 的第一条下游边。**两次它一次都没查过 `ad`。**
它查了 `astronomy-db` 与 `product-catalog`，发现都快，于是把
「**我查过的下游都不慢**」写成了「**没有慢的下游**」，把耗时归到了调用方自己。

**这是判据侧 None-vs-zero 在 agent 推理里的同构**：
`prom_rate_in_window` 把「样本不足」写成速率 0（决策 029），
agent 把「这条边我没去查」写成「这条边没问题」。
**取不到与取到零，在两个层面上是同一个错误。**

**代价**：`blackhole-ad-01` 因此连类别也一起错了 —— 15000 ms 的封顶 span 被读成
「注入了固定延迟」，于是 blackhole 判成 latency。**一个未查的边同时吃掉了服务和类别两半。**

**尚未修**：本轮 prompt 冻结（留出集测试的前提），未改。
可选的修法有两条，都要等下一次 prompt 迭代：
(a) 把「排除下游之前必须逐条枚举 `topology` 里该服务的全部出边」写成硬步骤；
(b) 给 `traces_query` 加一个按调用方展开全部下游边的调用形状，
让「枚举」不依赖模型自觉。**(a) 是 prompt 改动，(b) 是工具改动，代价与风险不同。**

**证据**：`artifacts/agent_runs/holdout11_agent_20260906/latency-ad-800.json`、
`.../blackhole-ad-01.json`（两份 transcript 的 `traces_query` 参数逐条可查）、
`evidence/_shared/topology.json`。

### 1.5 步数耗尽而不交卷（2026-09-06，开箱 haiku）

**现象**：43 张里 **9 张**（20.9%）跑满 20 步、`terminated=max_steps`、
**一次 `submit` 都没调**，答案是 `None`。同一批卡上 **agent-sonnet 是 0/43**，
43 张全部以 `submit` 收尾。
九张：`crash-astronomy-db-01`、`latency-cart-800`、`latency-email-800`、
`blackhole-frontend-01`、`misconfig-payment-75`、`blackhole-astronomy-db-01`、
`blackhole-ad-01`、`latency-ad-800`、`latency-recommendation-3000`。

**不是卡在循环里。** 逐份查工具调用参数：`blackhole-ad-01` 20 步里打了
**35 次工具调用，35 次参数各不相同**；`latency-cart-800` 23 次调用同样零重复。
它没有反复问同一个问题，而是**一直在问新问题**——
**查得越来越宽，就是不收敛到一个答案**。

**代价是双份的**：这九张的平均成本 **$0.1181**，
高于交卷那 34 张的 **$0.0659**（1.8 倍）。
**它失败最彻底的卡，也正是它最贵的卡** —— 步数熔断是唯一兜住成本的东西。

**参数校验计数同向**：`validation_rejects` 开箱 haiku **33** vs 调优 sonnet **4**（8 倍），
而 `nudges`（模型不调工具、用散文作答）**两边都是 0**。
所以格式问题出在**工具参数校验**上，不在「答成了散文」上。
按裁决 prompt 一字未调，**这两个计数如实记录，不作为改 prompt 的依据**。

**这一类为什么值得单列**：§1.1–1.4 都是「答错了」，
本条是「**没有答**」。前四类可以靠改 prompt 或改工具去纠偏，
本条的直接读法是**这个配置在这些卡上够不到**——
20 步的熔断对调优 sonnet 是从没碰到过的天花板，对开箱 haiku 是 21% 的卡的实际终点。
**抬 `max_steps` 能不能救，本轮没测**：那会同时动两臂的判据前提，
且按上面的成本数据，抬步数只会让最贵的那九张更贵。

## 2. 检测线三条实测

判据阈值不是拍的，三条线各有一次实测把它钉住。

### 2.1 规则 7 的 100 ms 绝对地板

规则 7（方法级 p95）的比例臂 `p95 ≥ 2 × 基线` 单独用会在**方法级小基线**上炸：
不加地板时首次重检产出 **46 条告警，其中 16 条 Δ < 100 ms**，
全部落在 6–36 ms 基线的方法上——比例是真的，绝对量毫无意义。
更糟的是它把 `crash-email-01` / `misconfig-payment-50` / `misconfig-cart-75` 三张
从**诚实的 `no_alert`** 翻成「有告警但指错服务」。

加 100 ms 地板后：被剔的 16 条 Δ **全部 < 45 ms**，
而 `latency-checkout-800` 的 **+902.5 ms**（比例臂 11.31×）不受影响——
地板砍掉的是噪声，没碰信号。

**证据**：决策 023「放弃了什么」、`docs/fault_schema.md` §10、O-P2-17。

### 2.2 10% 随机故障低于 120 s 窗的检测线（F-1）

`adFailure` 只让 **10%** 的 `GetAds` 失败，而规则 1/5 的阈值
`N = max(5, ⌈0.25 × 基线速率 × inject_s⌉)` 的相对项是**该方法调用数的 25%**。
**25% > 10%，无论流量多大都够不着。**

实测（`misconfig-ad-on`，120 s 窗）：`GetAds` 调用 17 次、报错 4 次、门槛 N = 7、
告警 **0 条**（规则 1–7 全部）。两轮检测均 `no_alert`，按决策 023 第 7 条**出库**（69 → 68 卡）。

> **低比例随机故障需要的是与「比例」对齐的判据形式，不是更低的阈值。**
> 把 N 的相对项降到 10% 以下能救这张卡，但会同时放松所有卡的规则 1/5，
> 干净窗负对照会立刻炸。正确形状是「注入窗报错占比**显著高于**基线窗」的比例差异检验。
> **这是评测集设计的缺口，不是检测器的 bug** —— 同一批规则在 crash / blackhole /
> 高比例 misconfig 上工作正常。

**证据**：F-1、决策 023 第 7 条。证据包 `evidence/misconfig-ad-on/` 保留为素材。

### 2.3 latency 的报错占比线 10%（F-3）

原判据第二个合取项是「注入期报错**一条都不许涨**」，其前提「纯延迟不产生报错」
**从 800 ms 起就不成立**——延迟把尾部请求推过上游超时，报错是延迟的真实后果。

落码前在**全部在库 latency 与 misconfig 卡**上模拟了两个候选：

| 方案 | latency 放行 | misconfig 误放 |
| --- | ---: | ---: |
| 现状（报错不许涨） | 5/8 | 0/7 |
| A 删掉该合取项 | **7/8** | **0/7** |
| B 报错占比 < 10% 不否决 | **7/8** | **0/7** |

**两方案区分度完全相同**，取更保守的 B。区分度本来就不由这个合取项提供——
由 p50 门提供：七张 misconfig 卡的位移是 **0.5 ms 或无定义**，离 640 ms 门槛差两个数量级。

两个数据点：**800 档 1.45%**（7/484 span）、**3000 档 8.70%**（2/23 span）。

> **警告（原文保留）**：3000 档只剩 **1.3 个百分点**余量。
> 若日后加更高档位，这条线要**连同实测一起重定**，不能沿用。

**批次四结论：这条余量在下一次运行就被花掉了。**
`latency-shipping-3000` 重跑，F-3 规则**正确适用**（p50 右移 2999.72 ms ≥ 2400），
仍被拒 —— 调用方报错占比 **12.0%（3/25）**，越过 10% 上限。
上一次同一张卡是 **8.70%（2/23）**。

> **两个数据点现在骑在线的两边，这正是「须重定」的信号本身。**
> 注意两次的绝对量都极小（3/25 与 2/23），比例的方差很大 ——
> 这一档的报错占比**不是一个能用单次观测钉住的量**。
> 本轮**没有**顺手把上限抬一档把卡放进来：那会把「按实测定线」变成「按需要挪线」。
> 该卡不进批次五，等一次专门的多轮测量。

**批次八（第三个数据点）：线没被证伪，但它的分辨率被量出来了。**
`latency-shipping-3000` 第三次重跑，报错占比 **4.76%（1/21）**，**过门入库**。
三次同一张卡：

| 运行 | 报错 / 总调用 | 占比 | 结果 |
| --- | ---: | ---: | --- |
| 首次 | 2 / 23 | **8.70%** | 过 |
| 批次四 | 3 / 25 | **12.0%** | 挂 |
| 批次八 | 1 / 21 | **4.76%** | **过** |

**结论：12.0% 那次是噪声，线不该挪。** 三次的绝对量是 **1、2、3 条报错**，
分母都在 19–25 之间 —— **这不是一个在 8% 和 12% 之间移动的量，是一个在
「一条、两条、三条」之间跳的计数**。在 n≈21 上，**每多一条报错就是约 4.8 个百分点**，
所以这条线的实际分辨率是四档：0 条 ≈ 0%、1 条 ≈ 4.8%、2 条 ≈ 9.5%、3 条 ≈ 14.3%。
**10% 恰好落在「两条」和「三条」之间的空隙里** ——
它区分的其实是「≤2 条」与「≥3 条」，而不是任何百分比。

**但同一批次也证明了这条线确实在分辨两种形态**，这是它最强的辩护：
同一档、同一规则下 `latency-quote-3000` 的报错占比是 **94.74%（18/19）**，
不是 1–3 条的噪声区，是**完全不同的量级**（见 §2.4）。
**在低报错端分辨率粗，不等于在高报错端没有区分度。**

**处置**：**线不动**（10%），但在 §2.3 记下它的真实语义是计数门而不是比例门。
真要按比例定线，需要把注入窗拉长到调用数 n ≥ 100 的量级，
那是另一次专门测量，不在本轮。

**证据**：决策 027、决策 037、commit `34f4d3c`（落码后回放 15 张卡与模拟逐张一致）、
`scripts/out/batch8_20260906T193745Z/summary.json`。

### 2.4 高档 latency 在某些靶子上越过调用方超时，形态从「慢」变成「错」（批次八新增）

**现象**：`latency-quote-3000` 注入 3000 ms，**症状门判失败** ——
p50 右移 **4998.75 ms**（远超 2400 门槛）却被 F-3 的报错占比项否决：
调用方边 **18/19 条报错，占比 94.74%**。

**关键的不是占比，是那个 p50**：注入 3000 ms，观测到的却是 **5001.49 ms**
（基线 2.74 ms）。多出来的约 2 秒不是注入给的 ——
**是调用方在等一个约 5 秒的超时，然后报错**。
`quote` 是 PHP 服务、被 `shipping` 以 HTTP 调用，这条边上有一个约 5 s 的超时；
800 档（+800 ms）不会碰到它，3000 档在排队叠加后会。

**读法**：**同一个原语在同一个靶子上，档位跨过某个阈值之后产出的不是同一类故障。**
低档是 latency（慢而不错），高档变成 error（超时即错）。
F-3 的报错占比项把它拒掉是**正确行为** —— 那张卡的真值是 `latency`，
而证据面上它长得像 `misconfig`/`crash`。**放它进来会往评测集里塞一张标签错的卡。**

**与 §1.1 的关系**：§1.1 说的是 agent 在 harvest 视角下把 crash 读成 blackhole，
是**读的人**弄错；本条是**卡本身**在高档下变成了另一类，是**出题的人**要处理的问题。
两者都表现为「类别对不上」，但一个改 prompt、一个改配方。

**未定**：这张卡该出库、该降档、还是该把真值改成 `misconfig` —— 本轮不裁决，
见 [O-P2-24](open_items.md)。**它不入库**，配方保持 68。

**证据**：`scripts/out/batch8_20260906T193745Z/summary.json` 第 9 周期、决策 037。

## 3. 低流量 × 判据类型矩阵

低流量靶子（`checkout` / `email` / `payment`，五窗 0.0433–0.0633 /s）是本项目最集中的
麻烦来源。但**「低流量」不是一种问题，是三种**，取决于压在它上面的判据类型：

| 判据类型 | 低流量下的表现 | 可救否 | 修法 |
| --- | --- | --- | --- |
| **计数判据**（报错数 > N、静默臂） | 期望调用数压在阈值地板上，样本量不够 | **可救** | **加窗**：R1 把 `inject_s` 拉到 300、F-2 把 `recover_s` 按速率算 |
| **分位数判据**（p50 位移） | 曾被判为「该流量下物理不可判」 | **可救，但原判是错的** | 实为**查询缺陷**：边一直在，探针没匹配上（F-6） |
| **任何判据 × 取不到值** | 取不到被当成零，与真实为零不可分辨 | **已修（决策 029）** | 七处统一改为「不适用」，见 §3.3 |
| **任何判据 × 边无埋点** | 观测**根本不存在**，不是被误读 | **不可救** | 加窗、改判据、修匹配全部无效；只能修埋点或出库（F-8） |

### 3.1 计数判据：加窗有效（R1 / F-2）

**R1**（注入窗）：`checkout`/`email`/`payment` 的 120 s 窗期望调用数约 **6.8**，
而两条判据地板（`N ≥ 5`、`基线速率 × inject_s ≥ 5`）就压在这个数上。
批次 2 实测 `crash-checkout-01` 报错 span **4 / 门槛 5** 差一条，
靶子侧臂因 4.8 < 5 判「不适用」，**两臂同时因样本量失效**。
`inject_s=300` 把期望抬到约 **17**。效果：三张此前 `no_alert` 的卡全部翻盘
（`misconfig-payment-75` 0→5、`misconfig-payment-50` 0→5、`crash-email-01` 0→1）。

**F-2**（恢复窗）：R1 只改了注入窗，恢复窗仍是 30 s。0.0433 /s 下期望 **1.3 次调用**，
而门槛「速率 ≥ 基线 × 0.5」等价于「至少落 1 次」。
实测两张失败卡：`crash-payment-01` 期望 1.6 实收 0、`blackhole-payment-01` 期望 2.5 实收 0，
残留探针均干净。修法与 R1 **同构**（走 `cycle_override`，不另起覆盖路径），
`recover_s ≥ 30 + 5/速率`，落到 150 / 90 / 70 s，共 34 张卡。

**批次四结论：F-2 生效。** `crash-payment-01` 与 `blackhole-payment-01` ——
两张此前连挂两次 recovered 的卡 —— 在 `recover_s=150` 下**双双过门入库**。

> **残留风险（已量化，未消除）**：门槛取「期望 ≥ 5」只是压住而非消掉。
> recovered 要求 λ/2 次调用落窗，λ=5 时**仍有 12.5% 假失败率**。
> `ad` 恰好卡在线上（期望 **5.20 ≥ 5**，不加窗，假失败率 **10.9%**）。
>
> **但批次四证明这个残留风险不是 `blackhole-ad-01` 挂掉的原因。**
> 该卡第四批再次 recovered 失败，实测却是：调用方臂健康（6 条基线回来 5 条）、
> 速率臂通过（0.1667 ≥ 0.05）—— **失败在靶子侧臂把 spanmetrics 的导出滞后读成了静默**
> （计数器在 30 秒恢复窗里一动没动，Jaeger 同期已见 5 条 span）。
> 同批 `blackhole-recommendation-01` 完全同型。
> 因此**预授权的 `MIN_EXPECTED` 5→10 没有执行**：它只会顺带救 `ad`（期望 6.3 < 10），
> 救不了 `recommendation`（12.6 ≥ 10），是按错误机制打的补丁。
> 正确修法是导出间隔守卫（决策 029），离线回放证实两张卡都因此翻盘，已进批次五复跑。

**证据**：决策 023 R1、决策 027、决策 029、commit `34f4d3c`、O-P2-21。

### 3.2 分位数判据：曾被误判「物理不可判」，实为查询缺陷（F-6）

`latency-payment-800` 的 `caller_all_dur.p50` **恒为 null**，四个窗口全是 0 条调用方 span。
自然读法是「该流量下分位数物理不可判，出库」。**这个读法是错的。**

Prometheus 同期看到 17 次调用（0.0567 /s），而且**证据包里躺着 47 条
`checkout → payment` 父子边**。数据一直在 Jaeger 里，是探针没去找：

| checkout 的 client span | peer 标签 | 协议 |
| --- | --- | --- |
| `PaymentService/Charge` | `server.address=172.18.0.16` | gRPC |
| `CartService/GetCart` | `172.18.0.23` | gRPC |
| `CurrencyService/Convert` | `172.18.0.13` | gRPC |
| `ProductCatalogService/GetProduct` | `172.18.0.17` | gRPC |
| `POST`（→ shipping / email） | `shipping` / `email` | HTTP |

**同一个 checkout 进程，HTTP 出口给服务名、gRPC 出口给容器 IP**，
而匹配是 `peer 字符串 == 服务名`——checkout 的四条 gRPC 边**恒为空**。
一直没被发现，是因为那些靶子还有别的臂可走；
**`payment` 是唯一只有 checkout 一个调用方的靶子**，所以只有它把洞完整暴露。

修后实测（600 s 实时窗）：`payment` **0 → 38 条**（p50 2.78 ms），
`cart`/`currency`/`product-catalog` 从「仅 frontend」补上 checkout，其余靶子一条不少。
300 s 窗约 19 条足够出 p50，800 ms 相对 2.78 ms 是约 **290 倍**台阶。

**批次四结论：F-6 生效。** `latency-payment-800` 实测 caller p50 右移
**800.15 ms**（门槛 640），过门入库 —— 一张此前每一次运行 p50 都是 `null` 的卡。
**边一直都在，让它可见的是把容器 IP 反解成服务名。**

> **与 §3.1 成对**：低流量 × 计数判据是**真的样本不够**，加窗能救；
> 低流量 × 分位数判据这一次**根本不是流量问题**。
> 两者的观测长得一样（判据取不到值），处置完全相反。

**证据**：F-6、决策 027、commit `c4ef218`。

### 3.3 None-vs-zero：同一类 bug 出现两次，已审计未修

「分子取不到」被当成「分子是零」已发生两次，**都花了整整一轮才定位**：

| 次序 | 卡 | 表面症状 | 真因 |
| --- | --- | --- | --- |
| 1（批次 2） | `latency-frontend-800` | `caller p50 = null` | `PEER_KEYS` 不认 Envoy 的 `upstream_cluster` 命名（R3） |
| 2（批次 3） | `latency-payment-800` | `caller p50 = null` | checkout 的 gRPC peer 是容器 IP（F-6） |

**两次是同一类 bug，而 R3 的修法是「再加两个命名键」**——一次修一个键，
没有回头问「还有多少地方在把取不到当成零」。

第三步做了那次没做的回头看：**25 条判据路径逐条审计**，结论
**正确 11 / 可接受 9 / 错误 5**。五处错误中四处「取不到 → 判失败」（代价是重跑一张卡），
**一处「取不到 → 判通过」**：

> `judge_recovered` 的 misconfig 分支 `got = ase.get("server_error_spans") or 0`，
> `return got == 0`。trace 采集整体失败 → `got = 0` → **判已恢复、放行**。
> 复验：同一场故障下 misconfig 恢复门返回 `True`、crash 症状门返回 `False` ——
> 两者都不该给出裁决，现在一个给了通过、一个给了失败。
> **这是唯一会让一张证据不实的卡进库的路径，且入库后没有任何环节会回头查它。**

`target_side_arm` 已经是正确样板（`(None, {"applicable": False, "why": ...})`，
docstring 明写「否则又是一个静默的零分母」）。五处照抄即可，
但**根治要在采集侧分开「查过但没有」与「根本没被查」**，
而不是每出一例就加一个 peer 键。

**2026-08-29 收口**：批次四又撞出**两条审计漏掉的同族缺陷** ——
`prom_rate_in_window` 把「样本不足」写成速率 0.0，
以及 `target_side_arm` 在**短于 spanmetrics 导出间隔**的窗口上求值
（计数器是阶梯函数，两次导出之间恒平，速率恒为 0.0 与流量无关；
实测恢复窗开启后计数器平了 90–105 秒才跳，同期 Jaeger 已见 5 条与 9 条 span）。

**七处全部落码**（决策 029），统一为 `(None, {"applicable": False, "why": ...})`；
采集侧加 `caller_edges_queried` / `caller_match_method` / `callers_queried_names`
三个溯源字段，让「问遍了没人调」与「我们没去查」可分辨。

**追溯核查零命中**：41 张在库卡 × 四窗快照逐一检查，无采集错误、无缺失键；
7 张 misconfig 卡的 after 窗 `self_edges` 全部存在。
**假通过路径是真实缺陷，但从未实际放行任何一张卡。**

> **审计本身也会漏。** 25 条是读代码找出来的，2 条是让批次撞出来的。
> 代码审计覆盖得了形状，覆盖不了「我没想到这里也是一次测量」——
> `prom_rate_in_window` 看着像工具函数不像判据路径，
> 而导出间隔是**根本没出现在代码里的物理量**。

**证据**：`docs/probe_audit.md`（27 行审计表）、F-6、F-8、决策 023 R3、决策 028、决策 029。

### 4.5 开箱配置 haiku 4.5 vs 调优 sonnet 5（2026-09-06）

**这一节不是模型对照，口径必须先说清楚。** 主 agent 跑的是
`thinking={"type":"adaptive"}` + `output_config.effort="high"`，
而 **Haiku 4.5 这两个参数一个都不接受**（2026-09-06 实测：
adaptive thinking 返回 400 `adaptive thinking is not supported on this model`，
effort 返回 400 `This model does not support the effort parameter.`）。
它自己的思考开关是 `budget_tokens=N`，而 N 在这里没有任何实测依据。
所以本节比较的是 **开箱配置的 haiku 4.5**（无思考、无 effort）与
**调优过的 sonnet 5**（adaptive 思考、effort=high），
**两者之间差的不只是模型**。除此之外两臂完全相同：同一份 v2 prompt、
同 6 工具 + submit、同五道保险、同 `max_steps=20` 与 `max_usd_per_card=0.20`。
拆分「模型贡献」与「配置贡献」需要第三次运行，本轮没做，**不要从这两张表里推那个拆分**（决策 034）。

## 5. 评测卫生

这几条是让上面所有数字**值得引用**的前提，不是锦上添花。

### 5.1 泄漏 fail-closed，在花第一个 token 之前

`card_id` 这样的取值（`crash-cart-01`）字面写着 (service, class) **两半答案**。
它在 `task.json` 白名单里（管线按它寻址证据包），但**必须不进模型输入**。

四道自检在**首个 API 请求之前**跑，任一不过即中止：
`no_forbidden_keys`（六个决定答案的卡字段不得整键出现）、
`no_card_id`（**按值**查，唯一一条按值而非按键的检查）、
`fixed_prompt_and_tools`（system prompt 与工具 schema 与无卡时逐字节相同）、
`user_turn_subset_of_task_json`。

> **白名单字段 ≠ agent 可见字段。** 白名单管**打包寻址**，
> agent 输入只含 `trigger` + `agent_visible_symptom` 两项。
> 两者是两件事，`task_view.py` 顶部注释写明了这个区分。

CI 门 1 每次 push 复跑，共 12 项。

**证据**：决策 024、`scripts/agent/leak_check.py`、`scripts/harness/task_view.py`、
`tests/test_agent_no_leak.py`、commit `5193cd1`。

### 5.2 开发集是显式清单，不是运行时扫描

19 张卡写死在 `config.yaml`，**不在运行时按条件扫描**——
否则一个批次在两次评测之间落地，就会**悄悄改变「开发集」的含义**，
而两次的数字看起来仍然可比。选取条件与排除理由（6 张正在被重跑、包在改写中）
一并写在清单旁边。同理，三臂对照的 27 卡与留出的 5 卡各自冻结成文件。

**证据**：`scripts/agent/config.yaml`、`scripts/baselines/cardset_27.json`、
`scripts/baselines/cardset_holdout5.json`。

### 5.3 一次迭代纪律与冻结

prompt 迭代的判据**在动手之前**定死：**top-1 变好则 v2 定版，变差则回滚 v1 并记 finding**。
不做「再调一版看看」——19 张卡上单张值 5.3 个百分点，多轮微调等于在噪声上拟合。

实际结果 52.6% → 57.9%，按判据 v2 定版。
**即使发现了 F-5 那段写坏的材料也没有破例重改**——
冻结判据是在看到数字之前定的，看到数字之后为了更好看的结果给自己开例外，纪律就不存在了。
修正留档 F-5，等下一版（触发条件写死：卡集扩大后重测基线）。

**证据**：决策 025、F-5。

### 5.4 判分与执行分家

`run_agent.py` **不 import** `scripts/scenarios/cards.py`——**结构上看不见答案**，
因此也无法判分。`run_eval.py` 是唯一读 `scenarios/` 的一侧，从 transcript 判分。
同理，两条基线读 `EvidencePack`，它只能看见 `evidence/<card>/`，
`scenarios/` 在模块层面不可达。

**证据**：决策 024、`scripts/agent/run_agent.py`、`scripts/baselines/signals.py`。

### 5.5 检测器的负对照

判据只证明「有故障时报警」不够，还要证明「没故障时不报警」。
两份干净观察窗（一份无标签验规则 3/5、一份带标签覆盖 1–7）
在规则 1–7 下**均 0 条告警**，且已固化为 CI 门 3 的 fixture，每次 push 复跑。

**证据**：决策 028、`tests/test_clean_window_negative_control.py`、O-P2-17。
